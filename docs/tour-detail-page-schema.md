# Tour Detail Page — Content Audit and Schema Proposal

*Prepared 1 September 2026 · Reference page: `https://50plusvoyagers.com/grouptour/spain-portugal.html`*

---

## 0. What this document is

The client asked us to build the new tour detail page and make sure the database can hold
everything it needs. This document does three things, in order:

1. Audits what the live Spain–Portugal page actually contains, block by block.
2. Checks each block against what we already have, and says plainly where it lives today.
3. Proposes the smallest set of new tables that closes the gap — with the reuse decisions
   spelled out, including the two places where we should **not** create anything new.

Nothing has been created. The migration in §6 is written but not run.

---

## 1. The finding that matters most

**The new design does not currently hold real tour content. It generates it.**

This is easy to miss because the page looks complete. Three of its main sections are not reading
per-tour data at all:

| Section on the new page | Where its content comes from today |
| --- | --- |
| Day-by-day itinerary | **Generated by an algorithm** — `itineraryFor()` in `frontend/src/site/data/tours.ts` invents days from the places list and the duration string |
| What's included | **One shared list** — `tourInclusions`, identical for all 20 tours |
| What's excluded | **One shared list** — `tourExclusions`, identical for all 20 tours |
| "Why this trip" reasons | **Generated** — `reasons()` restates the duration and region as prose |

For a design mockup this is the right call, and the file says so honestly. But it cannot go live
against real tours:

- Spain–Portugal's 13 days are real, written days with hotels and meals per day. The generator
  produces *"Arrive in Porto — met on arrival and driven to the hotel"* and similar filler.
- Spain–Portugal excludes **TCS on foreign tours** and requires a **Schengen visa**. Coorg, a
  four-day domestic trip from Bangalore, excludes neither. A shared exclusions list is wrong for
  both of them.
- The included items on the live page each carry a **thumbnail photograph**. The shared list is
  plain strings.

So the work is not only "add some columns". It is giving these three sections a real source.

## 3. Reuse — what we should *not* build

The client asked us to reuse rather than duplicate. Three real opportunities, and they were
anticipated: two existing tables already carry a `tour_id` column put there for this module.

| Existing | Reuse? | Why |
| --- | --- | --- |
| **`feedback`** | ✅ **Yes — block 20** | Already has `customer_name`, `customer_location`, `feedback_text`, `rating`, `is_featured`, `display_order` **and `tour_id`**. It is exactly the testimonials block, with an editor's approval step the live page's hard-coded quotes do not have. **No testimonials table is needed.** |
| **`gallery_items`** | ⚠️ **Partly** | Has `title`, `caption`, `image_*`, `is_featured`, `display_order` **and `tour_id`**. This is the *gallery* — photographs from the road, shown on the homepage and gallery page. The tour page's carousel is a different job: ordered, page-specific, and its `alt` text must be mandatory. Recommend a separate `tour_images`, and keep `gallery_items.tour_id` for "photos from this tour" in the gallery. Reusing one table for both would mean a gallery photo silently appearing in a tour's carousel. |
| **`tours`** | ✅ **Yes — extend it** | The 5-column CRM table we built in the last step. The page-level fields (blocks 1–8, 13, 21, 22) are added here rather than in a new parallel table. |
| **CRM `tb_group_tour`** | ✅ **Read, never copy** | Price, dates, nights and booking status live there (blocks 10–12). Read live so the page can never disagree with the CRM. |

**On `tb_trf_*` and `tb_feedback_responses`** — worth restating: these hold medical conditions, blood
groups, nominee details and signatures. Nothing in them should be reachable from a public page. The
testimonials block uses our `feedback` table, which has an editorial approval step; raw CRM feedback
does not, and one row in the CRM dump names a traveller's medical history.

## 4. What is genuinely needed

Six new tables, plus columns added to the existing `tours`. Every new table is a **list** the page
repeats — which is precisely why each needs to be a table rather than a column.

```
tours                          (EXISTING — extended with page fields)
  │
  ├──< tour_images             NEW — carousel, block 5
  ├──< tour_highlights         NEW — bullets, block 8
  ├──< tour_itinerary_days     NEW — block 9, the big one
  ├──< tour_inclusions         NEW — block 14, each with a thumbnail
  ├──< tour_exclusions         NEW — block 15
  └──< tour_booking_steps      NEW — blocks 16 + 19 (numbered lists)

feedback ──────────────────────► REUSED via existing tour_id, block 20
gallery_items ─────────────────► left as it is
tb_group_tour (CRM) ───────────► read-only: price, dates, nights, status
```

### Why these six and not fewer

- **`tour_inclusions` and `tour_exclusions` are separate tables**, not one with a flag. Inclusions
  carry a thumbnail image; exclusions never do. One table would mean a column that is null for
  every exclusion row by definition.
- **`tour_booking_steps` covers both numbered lists** (how-to-book, documents-required) with a
  `kind` column, because they are structurally identical — a number and a paragraph. Two tables
  would be the same schema twice.
- **Travel & health guidelines (block 17)** also fits `tour_booking_steps` as a third `kind`.
- **Visa prose (block 18)** is a single value, so it is a column on `tours`, not a table.

The 5 CRM columns stay exactly as the client gave them. These are added beside:

| `subtitle` | varchar(255) null | 4 — the places line |
| `region` | varchar(20) null | India / International |
| `summary` | text null | 7 — highlights prose |
| `ribbon_text` | varchar(80) null | 6 |
| `route_map_disk` / `route_map_path` | varchar null | 13 |
| `visa_html` | text null | 18 |
| `booking_fee` | integer null | 21 |
| `balance_due_days` | smallint null | 21 |
| `meta_title` | varchar(255) null | 1 |
| `meta_description` | varchar(500) null | 1 |
| `meta_keywords` | varchar(500) null | 1 |
| `og_title` / `og_description` | varchar null | 2 |
| `og_image_disk` / `og_image_path` | varchar null | 2 |

**SEO note:** `meta_title`, `meta_description`, `meta_keywords` and the `og_*` fields are carried
across **verbatim** from the existing HTML. The client was explicit that meta and H1 tags should
stay as they are; these columns are what makes that possible rather than aspirational.

## 6. The child tables

| Table | Columns beyond `id`, `tour_id`, `display_order` |
| --- | --- |
| `tour_images` | `image_disk`, `image_path`, `alt` **NOT NULL**, `caption` null, `is_cover` bool |
| `tour_highlights` | `body` text |
| `tour_itinerary_days` | `day_number` smallint, `heading`, `title` null, `body_html` text, `stay` null, `meals` null, `day_date` date null |
| `tour_inclusions` | `body_html` text, `image_disk` null, `image_path` null |
| `tour_exclusions` | `body_html` text |
| `tour_booking_steps` | `kind` varchar(20), `step_number` smallint, `body_html` text |

Every child has `tour_id` → `tours(id)` `ON DELETE CASCADE`.

`alt` is not nullable on purpose: the accessibility and SEO checklist requires it, and a nullable
column is a promise nobody keeps.

`tour_booking_steps.kind` takes `booking` (block 16), `documents` (block 19) or `guidelines`
(block 17).

### On `day_date`

The live page hard-codes a date on every day — *"23 September, 2026"* thirteen times. When the tour
runs again next year all thirteen need editing by hand, and the Coorg page already shows the failure
mode: five dates, all needing a manual change.

**Recommendation: derive it** from the CRM's `tour_start_date + (day_number − 1)`. One CRM change
re-dates the whole itinerary. `day_date` stays as a nullable override for the tour that genuinely
needs one.

## 7. What still needs a decision

| # | Question | Why it matters |
| --- | --- | --- |
| 1 | **Is the design's generated itinerary acceptable as a fallback**, or must every published tour have real days? | If real days are required, 32 pages of HTML must be migrated before launch — that is the largest single task in this module. |
| 2 | **Confirm inclusions/exclusions become per-tour.** | The shared list is wrong for both Spain–Portugal and Coorg. Confirming this is what justifies two of the six tables. |
| 3 | **Where do the tour images come from?** | The client said images live in folders on the old server. We need them, or a decision to re-shoot/re-use the existing library. |
| 4 | **Confirm testimonials come from our `feedback` module**, not the CRM. | Keeps an editor's approval step between a traveller's words and a public page. |
| 5 | **Does the new design get the missing sections?** | The design has no route map, visa section, how-to-book steps or documents list. Either they are added to it, or that content is dropped from the new site — which would be a real content loss on pages that already rank. |

Question 5 is worth the client's attention. The old page carries them; the new design does not yet
have a place to put them.

---

## 8. Recommended order

1. Migration: extend `tours`, create the six child tables. *(No visible change; nothing breaks.)*
2. Models, admin CRUD, and the tour-page editor screens.
3. Content migration for two tours by hand — one domestic, one international — to prove the shape.
4. Wire the new detail page to the database, keeping the generator only as a fallback for a tour
   with no itinerary rows.
5. Migrate the remaining 30 pages.
6. 301 redirects from `legacy_url`, then launch.

Step 3 is deliberately before step 5: proving the schema on Spain–Portugal and Coorg costs two days
and is what stops us migrating 32 pages into a shape that turns out to be wrong.
